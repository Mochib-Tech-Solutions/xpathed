# Hosted workspace deployment

The hosted workspace follows `main`, separately from the published-image release flow. The **Deploy hosted workspace** job runs after the aggregate **Check** succeeds on a push to `main`, including runs with intentionally skipped test jobs. **Verify deployment result** then fails the workflow if deployment was unexpectedly skipped or failed. PRs, merge groups and manual CI dispatch cannot access deployment credentials. A superseded revision is skipped before opening SSH. Deployment jobs are serialized without cancelling an active deployment; the receiver also takes a host lock.

The job archives the exact checked revision and sends it over SSH with a pinned host key. A fingerprint of Docker build inputs and deployment scripts is compared with the last successful host receipt. Documentation, evaluation and standalone tests outside Docker build inputs do not rebuild or restart the app, but unchanged inputs still verify the running stack's health before reporting success. Failed health checks preserve the receipt and fail deployment without rebuilding or restarting. Files copied into a build context, including colocated Web tests and build configuration, conservatively count as application inputs. A failed earlier deployment does not advance that receipt, so the next eligible push still detects its missing changes. Changes to application package manifests conservatively rebuild the app.

The VPS builds the four runtime images before switching the existing Compose project. It checks the public HTTPS workspace, ClientApi and Browser health endpoints, plus Resolver health over the private Compose network. These checks make no provider calls. Failed builds leave the stack untouched; a failed switch or health check restores the previous source configuration and images, verifies their health and fails CI. This restores application containers, not browser sessions: runtime updates can close active sessions. After successful health checks, deployments retain only the current revision’s application images and remove all older xpathed image tags, including the previous revision, and stopped containers tied to those obsolete images. Unchanged deployments apply the same cleanup after verifying health. Unrelated resources, volumes and build cache are preserved. Cleanup never forces removal of an image used by a container; incomplete cleanup is reported without rolling back a healthy app. Source directories remain available for inspection. The production Browser image shares the pinned ASP.NET runtime base with the other APIs and installs only the package-matched Chromium browser, its system dependencies and x11vnc. It excludes the .NET SDK, Firefox, WebKit and the separate Chromium headless shell. The development target keeps the full Playwright SDK image for `dotnet watch`.

## Credentials and host setup

Repository Actions secrets contain `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS` and `DEPLOY_PUBLIC_URL`. The last value is the public HTTPS origin, without credentials, query or fragment; it must match the host's private `deploy/public-url`. The dedicated key has no interactive shell, forwarding, agent forwarding or PTY: its `authorized_keys` entry uses `restrict,command="python3 /home/ubuntu/xpathed/deploy/receiver.py"`. The receiver accepts only `deploy COMMIT_SHA INPUT_FINGERPRINT` and a bounded tar archive. Keep the receiver outside uploaded source; install `scripts/deployment-receiver.py` there using an administrative SSH session. Receiver changes require that administrative installation as well as a source merge.

Keep actual deployment addresses out of tracked files, GitHub issue/PR text, workflow summaries and environment URLs. Deployment registers GitHub masks for the public origin, its hostname and the SSH address, and independently redacts both subprocess output streams before printing them, including unsuccessful SSH commands. The host receiver also redacts worker stdout/stderr using `deploy/public-url` and optional `deploy/private-log-values` (one additional deployment hostname or IP per line, mode 0600). Keep these private files outside uploaded source. The receiver reports generic errors rather than tracebacks containing command arguments. Logs retain build progress, source identity, health failures and exit status without a deployment link. This does not make a public site undiscoverable: public DNS and TLS certificates still expose its hostname; security controls remain necessary.

The existing host directory contains `deploy/application.env` (runtime OpenRouter settings), `deploy/compose.hosted.yaml` (restart/logging/image settings and the HTTPS gateway), `deploy/Caddyfile`, `deploy/public-url` and `deploy/current.json`. Credentials stay in mode-0600 host files, outside archived source. `current.json` records the successful revision, input fingerprint, source directory and optional image override. Initialize it from the running source and images before enabling automation. Docker, Compose, Python 3.12 or later, passwordless `sudo docker`, working HTTPS and the existing Compose project `xpathed-hosted` are prerequisites. Local tooling checks also use Python to test the receiver and rollback logic.

The gateway exposes only HTTPS/HTTP; Web's direct port stays bound to loopback and the three APIs stay private. It validates public browser origins before mapping the accepted hostname to the internal loopback contract. Chromium remains nonroot with its sandbox and seccomp policy enabled. The current hosted demo opens directly without HTTP Basic authentication, as requested. Anyone who can reach it can create sessions and submit paid resolution requests using the server's runtime key; session IDs are capabilities, not user accounts. The OpenRouter key is never sent to the client or deployment workflow.

## Public browser isolation

The anonymous hosted Browser must not reach private services, loopback APIs, link-local metadata addresses or the VPS itself. An HTTP-only URL check cannot enforce that across redirects, subresources, WebSockets, service workers or DNS changes. `scripts/deployment-network.py` installs actual IPv4/IPv6 OUTPUT rules inside only the hosted Browser's network namespace using host `nsenter` and iptables. Browser keeps its ordinary nonroot user, Chromium sandbox and seccomp policy; it receives no network-administration capability. The helper checks the Compose project/service identity before using a container PID. Atomic chain replacement preserves Docker and unrelated chains. Health verification compares ordered rules and requires the isolation chain to precede other OUTPUT rules.

Replies to incoming API/viewer connections remain possible. The only private outbound exceptions are Docker's embedded DNS at its original port 53 and the trusted loopback RFB relay on ports 5900–5915; hosted `MaxSessions` must not exceed 16. Private connections initiated before policy installation are also rejected. Globally routed public IPv4 browsing remains supported. Outbound IPv6 initiation is disabled rather than allowing transition addresses to bypass IPv4 restrictions; IPv6-only sites are therefore unavailable in this hosted profile. Local development and evaluation do not use this profile and retain private fixture access, case denominators and browser parity.

Install the profile administratively before enabling automatic deployment:

1. Install `scripts/deployment-network.py` as root-owned `/usr/local/lib/xpathed/network-policy.py`, mode 0644, under a root-owned directory. Host Python, Docker, iproute2 `nsenter`, iptables and ip6tables are required.
2. Copy `docker/hosted/browser-entrypoint.sh` into the private deploy directory and merge `docker/hosted/compose.security.yaml` into the existing `deploy/compose.hosted.yaml`. Resolve its mount to that absolute directory. Preserve the private image, logging, restart and gateway settings. Its per-container memory/CPU/process limits bound public workload resource exhaustion; exceeding them can terminate work or sessions within that container.
3. Install `docker/hosted/xpathed-network.service` in `/etc/systemd/system/`, then run `sudo systemctl daemon-reload` and `sudo systemctl enable --now xpathed-network.service`. The guard polls only the named hosted Browser and acknowledges a fresh startup nonce after installing and verifying both address-family policies. A missing/failed guard leaves Browser waiting, including after host/container restarts. Keep the service enabled. A changed host address requires restarting the guard to refresh its VPS-address exclusions.
4. Install `docker/hosted/Caddyfile` as the private gateway configuration, setting `XPATHED_HOST` in the gateway environment or substituting the owned hostname before installation. Validate a candidate with the pinned Caddy image before replacing the live file, then reload it. It rejects foreign/null origins, rejects cross-site and same-site API/viewer Fetch Metadata, hides private paths/server versions, and supplies security headers even on denial responses. Ordinary top-level links to the workspace remain supported. It deliberately adds no login screen. HSTS applies only to this hostname; it does not use `includeSubDomains` or preload.
5. Recreate Browser using the existing successful source and private Compose overlay, then verify `sudo python3 /usr/local/lib/xpathed/network-policy.py --verify` and run `python3 scripts/hosted-security-check.py https://YOUR_WORKSPACE_HOST` from a trusted checkout. The provider-free probe checks public health, denial headers, origins, Fetch Metadata, private paths, private-health navigation rejection, public browsing and viewer origin handling, and closes only its own disposable session. Verify again after a container restart. It never fetches metadata, enumerates sessions or submits model calls.

Host-owned helper, entrypoint, service and gateway updates require administrative installation, like receiver updates. They are not replaced by uploaded application source or rollback, so restoring a previous application revision retains the installed security policy. Source templates are included in deployment fingerprinting; edits alone cannot install host configuration. Deployment health checks require the installed guard's exact rules/readiness and HTTPS security headers before accepting a source switch or reporting unchanged inputs as healthy.

## Operations

The source stack supplies the positive request/concurrency/model-call defaults documented in [runtime limits](runtime.md#backend-and-model-usage-limits). Override them in the host's private `deploy/application.env` before applying a deployment. Health checks remain available when traffic is throttled. Keep a dedicated application key with a provider-side credit limit for restart-safe dollar spending protection; local call counters reset on deployment and rollback. A daily call allowance alone is not a daily dollar budget. Trusted evaluation overlays are not appropriate for the public hosted stack.

Check the deployment job and `deploy/current.json` to identify the running source. A docs-only merge can leave an earlier revision running because its application fingerprint is unchanged. To retry a failed deployment, rerun the entire push CI workflow while that revision remains the current `main` head; ordinary CI receipts require one complete attempt. If a newer revision exists, use its full successful push run instead. Manual CI dispatch validates source without deployment.

Rollback failure is a failed deployment requiring administrative repair; the previous receipt remains unchanged. Inspect container state without printing environment values. The running revision remains available for recovery during a failed deployment. After a successful deployment cleans older images, restoring an older source revision requires rebuilding its images. This pipeline neither publishes a GitHub release nor changes the release baseline or evaluation route.
