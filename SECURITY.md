# Security

Report suspected credential exposure privately to a maintainer through GitHub's **Report a vulnerability** option when enabled. Avoid posting credentials, customer page captures or authentication data in issues, PRs or public Actions artifacts. Revoke a compromised credential before editing or removing its public copy; deleting a file does not remove Git history.

Keep application keys in ignored local environment files or private VPS configuration. Deployment SSH credentials and pinned host identity belong to Actions secrets. PR and merge-group checks receive no deployment or provider secrets; hosted deployment runs only after successful checks on a trusted `main` push. Paid qualification, publication and monitoring are restricted to private repositories.

The **Security / Credential scan** check scans checked-out Git history using checksum-pinned Gitleaks with full redaction. Narrow allowlists cover reviewed source hashes, historical prose, an exact dummy privacy-test value and an exact fixed UUID fixture for startup nonce tests. Negative controls require credential-shaped values to be detected inside each allowlisted file category. Run `node scripts/security-check.mjs` locally; the helper downloads and verifies the pinned scanner on Linux amd64 and macOS arm64, or accepts an explicitly supplied matching `GITLEAKS_BINARY`.

The main-branch protection policy is recorded in [.github/branch-protection.json](.github/branch-protection.json): one independent approval, dismissal of stale approvals, approval after the latest push, resolved conversations and the Check, Conventional commits and Credential scan statuses bound to the GitHub Actions app. Administrators are exempt from this classic branch-protection enforcement by owner choice and can override its approval/check requirements; other contributors remain subject to them. Verify successful checks before an administrative merge. Force pushes and branch deletion remain disabled, with the separate default-branch ruleset still applying to administrators. GitHub must accept the policy remotely; the JSON file alone is not enforcement. An author cannot supply their own independent approval.

After a visibility change, verify branch protection again, enable GitHub secret scanning and push protection if available, require workflow approval for all outside contributors, and retain read-only default workflow tokens. The public demo is a separately owner-selected access policy: it exposes session creation and paid resolution to visitors without exposing the provider key itself. Origin checks and private service ports do not provide user authentication or spending limits.

The owner explicitly retains evaluation datasets and archived evidence. Sharing repository visibility also changes who can read published release assets and Actions evidence. A clean credential scan is not a certification that every archived page or dataset is public-domain, nonpersonal or licensed for redistribution.

Backend API traffic and model admission have shared rate/concurrency allowances; see [runtime limits](docs/runtime.md#backend-and-model-usage-limits). They reject excess work without queues or provider retries and retain accounting for disconnected calls. These process-local quotas reduce consumption but reset on restart and do not authenticate visitors or impose a dollar budget. Use a dedicated application key with a provider-side credit limit, separate from the evaluation key, for monetary enforcement.

Anonymous hosted browsing also requires [network isolation](docs/deployment.md#public-browser-isolation), not just URL validation or CORS. The host rejects Browser-originated private, loopback, link-local and VPS-address traffic at the packet boundary, except embedded DNS and the local viewer relay. IPv6 outbound initiation is disabled in this IPv4 hosted profile. The startup gate prevents Browser from serving before those rules are installed after deployment or restart. CPU, memory and process limits contain resource exhaustion within each container. Keep Chromium's nonroot sandbox and seccomp policy intact.

The HTTPS gateway rejects foreign/null origins and cross-site or same-site API/viewer requests identified by Fetch Metadata. It adds HSTS, restrictive CSP, anti-framing, no-sniff, referrer, permissions and no-store headers to successful and denied responses. Headerless API clients remain supported: these browser protections do not authenticate a caller or stop a bot from making ordinary HTTP requests. Session IDs remain capabilities; retain the separate model/key spending protections.
