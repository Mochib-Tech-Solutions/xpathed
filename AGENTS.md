# xpathed repository guidance

## Product and scope

xpathed is a Resolver API for converting English instructions into verified XPath expressions. Resolver is the core system; Browser is a replaceable service behind an HTTP contract, and the chat workspace is a client for manual testing and demonstrations. Read [README.md](README.md) for setup and scope; use [browser integration](docs/runtime.md#browser-integration) when changing the browser boundary and [docs/runtime.md](docs/runtime.md) for runtime behavior. Preserve the existing test client's behavior when maintaining it.

The implemented foundation is the managed browser in [issue #2](https://github.com/Mochib-Tech-Solutions/xpathed/issues/2). Submitting a website address creates the browser session and navigates to that site; noVNC displays one page without browser chrome. Keep the initial address field enabled and use it as the entry point. Manage tabs in the client workspace, keeping Chromium chrome hidden in the fullscreen noVNC view. Chat drafts and session history belong to their managed page; resolution always targets the active page. Keep the UI full-page and minimal: chat, tabs, browser, essential navigation and a confirmed **Close all tabs** action in the tab strip. Keep the initial **New tab** visible before a browser session exists so navigation does not shift the toolbar. Place + immediately after the tabs. Default to dark mode with a direct light/dark toggle and persist the explicit choice. **Reset chat**, shown with an eraser beside the Chat heading, asks for confirmation before clearing only the active tab’s draft and results. Use distinct sent and response messages with local timestamps, ordered as element type and accessible name, action, XPath, then verification. Images use their accessible name or an explicit unnamed fallback; do not infer identity from image pixels. Multi-target responses use separate numbered cards beneath one shared action. Match client responses to resolver outcomes and reason codes, retaining specific limitations and per-target failures. Label ambiguity explicitly and request a name, section or position without inventing competing targets. For blocked actions, replace the target card with one red explanation naming the target and the first specific blocking reason; omit XPath, verification and repeated state labels. Keep replies for other readiness states direct: target and XPath, useful limitations, compact time/cost; show the interpreted action, actual passed checks, specific readiness limits, state details and one preferred verified XPath directly; omit repeated instructions, generic no-action/untested-behavior disclaimers, redundant action-scope suffixes and website metadata. The chat composer resolves instructions through OpenRouter under the [resolution contract](docs/resolution.md). Chat cost details expose estimated and reported USD costs separately. Keep pricing lookup model-independent; see the resolution contract for caching, pricing provenance and unavailable data. Keep the browser-owned document/capture identities and XPath same-node verification intact. XPath selection prefers explicit test contracts and meaningful scoped semantics before ordinary IDs; preserve independent mutation labels and consult [the selection policy](docs/resolution.md#preferred-xpath) when changing ranking.

Accepted follow-ups removed the bundled fixture website, browser Smoke project, manual Inspect button and duplicate close control. Do not restore them from the older #2 wording. Future evaluation work has its own explicit scope. Resolution selects and highlights every found target; it does not execute the instruction or add autonomous browsing. Use thick black-and-white outlines entirely outside the visible target bounds, with no interior tint, for contrast across page colors and a brief locator spotlight for small targets, respecting reduced motion. Keep highlights during mouse movement and scrolling, and clear them on browser clicks/keypresses, a new instruction or page/capture invalidation.

The latest accepted scope is one action per command across one or more distinct current-view targets. The API exposes one current request and response shape. Follow [ADR-0024](docs/adr/0024-keep-one-resolution-implementation.md): keep one selected implementation and prompt in `main`, updated through Git; reproduce retired experiments from their recorded revisions. Describe behavior in documentation; use Git commits and content hashes to identify source and recorded evidence; keep prompts and behavior free of manual revision numbers. Read [ADR-0018](docs/adr/0018-scope-resolution-to-the-current-view.md) when changing viewport eligibility or CSS evidence. Read [ADR-0020](docs/adr/0020-treat-latency-targets-as-evaluation-metrics.md) when changing latency metrics or request cancellation; two seconds is an aspirational speed target, not a total-response cutoff. Keep partially visible, disabled and covered targets, scoped absence and pending provider accounting distinct. The current-view prompt treats missing candidates as scoped absence; completeness describes target enumeration, not existence. Match requested controls separately from scope containers and repeated descendant text. For spatial item selection, preserve whole repeated-item candidates, their child controls, capture-owned parent identities and the geometry-derived layout index; read [spatial item context](docs/resolution.md#spatial-item-context) before changing grouping or neighbor evidence. Preserve current-view membership revalidation for found and absent results, document-wide XPath uniqueness and current-view saved-locator mutation coverage; see the [current-view contract](docs/resolution.md#current-view-boundary). Read [ADR-0014](docs/adr/0014-resolve-one-action-across-current-page-targets.md) when changing cardinality, action interpretation, UI, storage or grading. Show the shared action once and one same-node-verified XPath per found target unless its action is blocked; mixed interactions and sequential workflows are unsupported as a whole. Keep passive inspection, completeness limits and request-owned charges intact. Accessibility-aware eligibility and passive readiness define the current contract; read the [state and action matrix](docs/resolution.md#eligibility-and-action-observations) when changing capture, naming or readiness. Read [ADR-0012](docs/adr/0012-keep-frame-context-separate-from-xpath.md) when changing nested frame identity, capture budgets or geometry, and [ADR-0011](docs/adr/0011-report-observed-readiness-and-one-xpath.md) for observed readiness and [ADR-0015](docs/adr/0015-keep-target-highlights-until-user-input.md) for persistent multi-target highlights.

## Architecture and ownership

Hosted workspace deployment follows successful `main` push checks; see [deployment operations](docs/deployment.md). Preserve comparison with the last successful application fingerprint, pinned SSH host identity, serialized deployments and verified rollback. Keep runtime keys on the host and deployment access in Actions secrets; the hosted demo's public access is an explicit owner choice. Source deployment does not qualify or publish a release.

For XPath text changes, preserve the distinction between sanitized candidate names and XPath string values. Verify saved locators after DOM mutations and keep hidden/editable values out of generated text predicates; see the [preferred XPath policy](docs/resolution.md#preferred-xpath).

Keep Resolver independently usable by API callers and evaluation runners. Browser integration uses `BrowserUrl` and serialized Common contracts; replacement implementations must preserve the documented semantics. Playwright/Chromium is the only verified implementation. Keep browser handles and implementation dependencies inside Browser, and client display concerns outside Resolver.

Before editing a service or tests, read its scoped `AGENTS.md`. Use `$xpathed-resolution-checks` for cross-service resolution verification.

- **Browser** owns live Playwright objects, session/page identity, serialized operations and display cleanup. Other services exchange records from **Common**, never browser handles.
- **Resolver** is stateless between requests. **ClientApi** forwards test-client requests to Browser and Resolver. Per-tab chat history lives in the Web workspace session; evaluation runners own their saved artifacts.
- **Web** owns the React workspace. Keep shared shadcn/ui controls in `components/ui/`, feature state in `features/`, and common helpers in `lib/`. Use semantic CSS theme tokens, strict types and effect cleanup.
- All three .NET APIs use `ControllerBase`, explicit attribute routes and constructor injection. Keep `Program.cs` for composition, middleware for request policies, and service behavior outside controllers. One named C# type belongs in a matching file with a folder-aligned namespace.
- All four local services run in Docker. Compose and per-service Dockerfiles live in `docker/`; use the root commands or `docker/compose.sh` so relative paths remain correct.

Keep independent localhost workspaces isolated with UUID session/page identities and show the connected session ID in the header. Keep session isolation, cancellation semantics, origin checks and the Chromium sandbox intact. Adopt new-tab links and popup windows as managed pages in the same session, within the tab limit. Keep the viewer and resolver on the active page, invalidating captures and highlights on tab switches. Closing all tabs must end the session, invalidate every previous page, clear its browser state and return to the initial address field. Treat page content and future model output as untrusted data; keep cookies, credentials, passwords and unrelated form values out of logs and model inputs.

For imported evaluation inputs, semantic review must include the exact prepared model input after Resolver privacy sanitization. Bind that input hash and reject drift before provider inference; imported JSON alone is not sufficient evidence of answerability. Preserve rejected preparation evidence and stop new calls on review-integrity violations.

## Commands and verification

Call the labelled cases the **evaluation set**, with **Saved-page selection**, **XPath construction and verification**, and **Live-browser Resolver** categories. Saved-page selection uses saved inputs. Live-browser Resolver uses a real Chromium page with either a controlled provider or live provider inference; identify the provider mode separately. Use regression for a lost pass in a comparison. Live-browser Resolver covers the complete resolution API pipeline; Web tests separately cover the test client. Preserve the release policy that blocks lost baseline passes.

Run commands from the repository root, using the RTK prefix required above. `package.json`, `global.json` and lockfiles are the executable sources for commands and versions.

Use Conventional Commits for every commit and PR title: `type(scope): description`, with optional scope and `!` for breaking changes. Dependency installation enables worktree-local `pre-commit` and `commit-msg` hooks. Before committing code, stage or set aside unstaged source/configuration so checks validate the intended commit. See [local commit checks](docs/ci.md#local-commit-checks) for selection, setup and CI enforcement limits.

- `pnpm run setup` prepares configuration and workspace dependencies; `pnpm dev` replaces the existing development runner for this checkout and Compose project, then runs Docker development mode. Preserve `.env`; never replace unrelated projects. A separate checkout needs its own `COMPOSE_PROJECT_NAME` and `XPATHED_PORT`.
- `pnpm check:dotnet`, `pnpm check:web` and `pnpm check:tooling` validate the affected area. `pnpm check` is the full local gate and runs independent groups concurrently. Keep shared .NET build outputs ordered; see [parallel execution](docs/ci.md#parallel-execution).
- `pnpm format` applies formatting; `pnpm format:check` verifies it. C# builds enforce the shared recommended analyzers and warnings as errors. Pinned CSharpier owns whitespace/wrapping at the `.editorconfig` 120-column target; native `dotnet format style` checks semantic style. Restore local tools with `dotnet tool restore`.
- `pnpm test:resolution` runs deterministic real-browser resolution checks in an isolated Docker stack; `pnpm test:resolution:live` explicitly exercises OpenRouter with the local API key. These remain outside CI service startup. Keep live tests on the documented cheap route, retain the output limit and report actual cost; runtime requests have no provider price filter; use deterministic responses for other checks.
- `pnpm evaluate` runs all three categories, including paid Saved-page selection and Live-browser Resolver, with `OPENROUTER_EVAL_API_KEY` and reviewed dataset inputs. Use `evaluate:model:live`, `evaluate:xpath` or `evaluate:resolver:live` separately; the XPath category starts only Browser and the fixture, with controlled selections and no model calls. `pnpm evaluate:resolver` retains the provider-free complete pipeline suite used in CI (up to four browser workers). `pnpm evaluate:replay RUN_DIRECTORY` regrades one category's saved evidence. Keep each category's denominator, exclusions and cost separate. App unit/integration commands stay unchanged. See [ADR-0025](docs/adr/0025-evaluate-selection-xpath-and-resolver-separately.md).
- `pnpm release:evaluate` runs the complete comparison using verified images and the saved-page Resolver worker. The underlying `pnpm evaluate:qualify` runner alone supports filtered Live-browser Resolver checks with a controlled provider; `pnpm evaluate:qualify:replay RUN_DIRECTORY` recomputes saved results without paid calls. Use `OPENROUTER_EVAL_API_KEY` for live evaluation. Apply the current policy to both arms and preserve case inputs, configuration, source/image identity, all outcomes and separate Live-browser Resolver and Saved-page selection denominators. Verify configuration consistency within each arm and category; retain their distinct scope and schema identities.
- Keep shared Live-browser Resolver and XPath cases in `evaluation/cases/`, controlled pages/oracles in `evaluation/fixtures/`, source adapters and reviewed collection metadata in `evaluation/datasets/`. Name shared XPath/Resolver cases and browser/pipeline test titles `<group>-<behavior>` using the behavior and expected result; retain prior case IDs in `sourceIds` when renaming or deduplicating. Keep one definition per case. Unit/integration/UI test organization stays unchanged.
- `pnpm datasets:collection pack IMPORT_DIRECTORY OUTPUT REVIEW_FILE...` builds the private reviewed input archive; `pnpm datasets:collection fetch` obtains the digest-pinned asset. Keep payloads under ignored `.artifacts/datasets/`; missing or changed required data cannot silently shrink a release run. See [collection setup](docs/evaluation.md#private-dataset-collection) for publication status and review requirements.
- `pnpm evaluate:compare` compares a verified Basic resolver bundle, the current Improved resolver and Stagehand. Use the [resolver comparison guide](docs/evaluation.md#resolver-comparison); keep one original attempt per arm and report category accuracy, gains, regressions and unavailable measurements. Generate current README tables and figures from the same complete audited-set evidence using the [figure exporter](docs/assets/evaluation/README.md); preserve separate category denominators and label earlier results as historical.
- For paid parallel continuation, read [research continuation](docs/evaluation.md#continue-a-research-comparison-in-parallel): preserve the frozen plan and completed arms, drain before resuming, and report execution cohorts separately. Release comparisons retain their serial runner.
- Preserve original dataset splits, reviewed input identities, prompt/settings provenance and unsupported observations. Develop experiments on branches; keep one selected implementation in `main`. Reported/unknown charges remain informational and cannot change failed outcomes.
- Release orchestration lives in `scripts/release/`; [the runbook](docs/releases.md) covers saved-image evaluation, evidence verification, merge-time publication and monitoring. Preserve caller-pinned digests, complete original evidence, source-tree and artifact identity, the release baseline and original retention deadlines. Verify archived images without rebuilding; packaging and replay alone do not establish a release. Keep existing charges and unknown amounts through cleanup. Report hosted execution, dataset publication, live checks and deployment only when actually verified.
- `pnpm docker:check` validates Docker definitions. `pnpm docker:build` builds images, and `pnpm docker:down` stops project containers.

Keep CI jobs independent and selected by relevant changes. The deterministic browser CI job builds and starts only Browser, Resolver and the evaluation fixture; full application-stack startup remains outside CI. Follow [the CI runbook](docs/ci.md) for exact-revision receipts, browser replay, artifact retention and whole-workflow reruns. Ordinary CI stays provider-free. Trusted `main` → `release` PR qualification and release monitoring use the dedicated evaluation key; keep their evidence and source-identity checks intact. Update `Xpathed.slnx` and `scripts/ci-changes.mjs` when adding projects. Validate behavior at the appropriate boundary; report actual checks rather than inferring success from configuration alone.

## Keep the guide current

When scope, commands, architecture or conventions change, update `README.md` and this file in the same change. Update `docs/runtime.md` for API/configuration/lifecycle changes, `CONTEXT.md` for domain terms, and an ADR for consequential accepted trade-offs. Remove stale instructions instead of accumulating contradictory history. Keep future work linked to its live issue; do not maintain a duplicate issue-status table or document test counts/inventories.

Research notes record dated evidence and alternatives, not automatic requirements. Verify version-sensitive API/package/model claims from official sources before relying on them. Keep commit, branch and PR wording focused on the change and use the configured human Git identity.

## Code Review Rules

- Check the requested issue and latest accepted scope; flag accidental feature expansion or claims that future roadmap items already work.
- Flag changes that let the viewer and resolver address different pages, preserve an invalidated session, bypass input/origin checks or weaken the browser sandbox.
- Keep shared contracts serializable and service dependencies within their documented ownership.
- Check that docs and affected CI selection match changed commands or project paths. Leave formatting and lint enforcement to configured tools.
